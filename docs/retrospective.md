# 开发复盘 —— moonvoice

> 赛事要求："可以使用 AI 辅助，但目标、路径与质量必须由参赛者掌握"（"这不是提示词比赛"）。
> 这份复盘回答三件事：**关键架构决策怎么定的**、**AI 工具在其中起了什么作用、在哪里出过错**、
> **参考了哪些开源工作**。

## 一、项目一句话

把「任意音频 → 可识别的语音段与特征」做成零依赖、可在 wasm 沙箱里跑的 MoonBit 库与 agent 技能。

## 二、关键架构决策

| 决策 | 备选 | 为什么这么选 | 代价 |
|---|---|---|---|
| **库包不依赖任何平台 I/O，只有 `cmd/*` 薄壳依赖 `miniio`** | 全库依赖 miniio | 发现 miniio **只支持 wasm 后端**；分层后库能在四后端测试，技能只需 wasm | 库内不能直接读文件（本来也不该） |
| **内部样本统一 f32、交错存储** | f64；或保持原始位深 | f32 的 24 位尾数足以承载 32-bit PCM 动态范围，内存减半 | 32-bit 样本落地会舍入（已写进测试容差） |
| **整数样本读写全程走 Double 运算** | 用 Int 位运算 | Int 是 32 位，`u32→i32` 会**静默回绕**；Double 的 53 位尾数精确可表示 | 略慢，但解析不是热路径 |
| **重采样用多相分解而非"插零+卷积"** | 直接卷积 | 直接卷积是 O(N×L×taps)，44100→48000（L=160）会慢 160 倍 | 实现复杂一些 |
| **VAD 的谱特征要有"否决权"** | 只做加权求和 | 实测：响亮白噪声突发能量比语音高 40 dB，纯加法得分无论如何压不住；只加不减的融合在突发噪声下退化成纯能量 VAD | 引入"有调性噪声会误判"的边界（已列入已知边界） |
| **噪声底在语音期冻结** | 全程自由跟踪 | 没有静音的素材里，自由跟踪会一路追着最轻的音节跑，把语音当噪声底（经典失效模式） | 需要"安全阀"防止长期冻结 |
| **测试数据内嵌进源码而非读文件** | 读 fixtures 目录 | wasm 沙箱没有文件系统；内嵌后四后端跑的是**同一套**金标 | 源码体积较大 |

## 三、工程方法：三条贯穿始终的做法

### 1. 金标对拍的参照物必须是独立实现

| 被测 | 参照 | 为什么不能用自己 |
|---|---|---|
| WAV 解码 | **libsndfile** | 自己写的期望值只会印证自己的理解 |
| 重采样 | **scipy.signal.resample_poly** | 同上 |
| FFT / STFT / mel / MFCC | **numpy.fft / librosa** | 约定极多（窗的对称性、mel 标度、归一化），自己定约定必然对不上生态 |
| 响度 | **pyloudnorm**（BS.1770-4） | 标准实现里有大量细节 |
| VAD | **构造真值** | 现成 VAD 本身是带偏好的黑盒；"我在第 1.0~2.0 秒放了语音"是构造事实 |

VAD 那条特别说明：**不用别的 VAD 当标准答案**——拿它当真理等于测立场而不是测实现。

### 2. 容差必须有出处，不能拍脑袋

- WAV：`u8/s16/s24/f32` 的样本是 k/2ⁿ（n ≤ 24），f32 尾数可精确表示 → **容差 0，逐样本相等**
- `s32/f64` 理论相对误差 ≤ 2⁻²⁴ → 取 1e-7
- FFT：先把同一算法在 numpy 重写一遍（相对误差 3.4e-16），确认误差来自 f32 样本存储 → 取 1e-6
- VAD：边界容差取 90 ms = **设计上 hangover 的宽度**（hangover 是刻意保留尾音，
  把这些帧算成误检等于用指标否定设计意图）

### 3. 先测后改，不做没有数字的优化

性能优化三步（每步都有 benches 数字）：

1. 消除分配 → **毫无效果**（分配不是瓶颈，这条反例留在注释里）
2. 去掉冗余边界检查（重采样内层 + FFT 缓冲改无检查访问）→ +22~43%
3. **缓存 Hann 窗**（此前每帧重算 512 次 `cos()`）→ wasm **+322%**

最终：VAD 从 419× 实时提升到 **1171× 实时**（wasm）。

## 四、AI 工具的作用（诚实分层）

### 工具链（据实说明）

使用 **Claude Code**（agent 框架，后端模型为 DeepSeek）完成代码、测试与文档的初稿；
方向、验收标准与质量把关由我负责（见下表 8 条判断）。

### AI 做了什么

- 全部代码、测试、金标生成脚本、文档的**初稿编写**
- 生态调研（mooncakes 下载量、skills 市场现状、可复用包评估）
- 调试：编译错误定位、把失败测试的原因追到根因
- 把"实测数字"整理成表格与结论

### 我是怎么用 AI 的：我在哪些点上做了判断

AI 负责动手，但**方向、标准与取舍由我定**。以下按实际发生顺序列出我做的判断，
每一条都改变了最终交付物：

| # | 我做的判断 | 它改变了什么 |
|---|---|---|
| 1 | **选题拍板**：AI 给出三个方向（语音前端 / Skill 质检工具链 / 音视频容器）与"9 月冲刺 vs 10 月稳做"的分析，我选了语音前端 + 9 月赛 | 决定了整个项目的立意与时间盒 |
| 2 | **"先测再说"**：反复要求 AI 拿实测数字说话，而不是凭直觉给结论 | 否掉了若干次没有依据的优化方向（例如"消除内存分配"那条，实测证明分配根本不是瓶颈）；也逼出了后面全部性能收益 |
| 3 | **定四条质量标准**：榨性能、提音频产出质量、接口要优雅、代码组织要以**可组合的原语**为单元 | 直接决定了后半程的工作内容：三条性能优化、位深保真/抖动/削波报告、接口审计、原语分层 |
| 4 | **纠正调研范围**：AI 一开始只查本机标准库就下"没有现成的"结论，我指出要看**公开生态**（mooncakes 上有没有可复用的包） | 促成了生态调研表（`mizchi/simd` 10339 下载可用、FFT 专用包最多 33 下载不宜依赖），避免重复造轮子也避免依赖不成熟的包 |
| 5 | **主动质疑质量**：直接问"性能、可维护性、接口是否达到你的开发水平" | 逼出一次接口审计，发现 `SegmentsResult` **只能序列化成 JSON、拿不到分段数据**——这是"作为库不可用"的硬伤，已修 |
| 6 | **定长期定位**：提出"要像 NumPy / FFmpeg 一样能当后续开发的基础" | 决定了从"一个 VAD 工具"扩展为分层原语库（并明确缺什么：流式、PCM I/O、FLAC） |
| 7 | **范围纪律**：拍板"先提交一个，基础库扩展等十月" | 阻止了项目在交付前继续膨胀，保证按时可交 |
| 8 | **仓库口径**：要求只放与项目本身有关的内容，删掉赛事行政笔记与脚手架残留 | 公开仓库里只有代码、测试、文档，没有与项目无关的东西 |

**一条经验**：AI 的产出质量对**提问的精确度**极其敏感。
问"优化一下性能"得到的是没有依据的猜测；问"性能瓶颈在哪、改完提升了多少"得到的是可核对的数据。
上面第 2、3、5 条之所以有效，都是因为把要求收敛到了可验证的形式。

### 与 AI 分工的一句话总结

**AI 提供的是速度与覆盖面**（一次写几百行、把四后端测试全跑一遍、把七个参照实现都对拍上），
**我提供的是判断**（做什么、什么算好、哪里不对劲、什么时候停）。
复盘里记录的 7 处 AI 错误，没有一处是 AI 自己发现并纠正的——全部由独立参照、性质测试，
或我对结果的不信任逼出来的。

### AI 出错的地方，以及怎么被发现的

这一节是本复盘最有价值的部分——**错误本身比成果更能说明 AI 工具该怎么用**：

| 错误 | 发现方式 | 教训 |
|---|---|---|
| ISTFT 里除了两次 n（输出被缩到 1/512） | "完全重构"性质测试 | 谱域处理写错不会报错，只会静默失效——**性质测试比示例测试强得多** |
| 响度块处理漏 `start` 偏移（每个块都在量开头，高估 2.5 LU） | 与 pyloudnorm 对拍 | 用 Python 复现自己的算法（与参照只差 0.005 LU）→ 确定问题在实现不在算法 |
| `top_db` 逐帧截断而非整图截断（与 librosa 差 18 dB） | 与 librosa 对拍 | 约定级差异，"跑通了"永远发现不了 |
| VAD 调参用单种子，声称 0.917、换种子实测 0.789 | 换种子复测 | **单种子调参 = 过拟合到那一次随机抽样**；改为多种子 + 最差场景目标 |
| 谱特征"只加不减"的融合在噪声突发下无效 | 三引擎对比测试 | 加法得分没有否决权 |
| 反复用 shell 生成含转义的代码 → 转义被吞、代码写坏 | 编译报错 | 工具链的地板效应，最终改为用编辑器直接写 |
| 忘了 `_` 不能做循环变量、`ref` 是保留字等 | 编译报错 | 语言细节靠编译器，不靠记忆 |

**共同点**：没有一个错误是被"读代码"发现的，全部由**独立参照**或**性质测试**抓出来。
这也是为什么这份工程把力气花在金标上，而不是花在堆功能上。

## 五、对开源工作的引用

- 本库**实现全部原创**，没有移植任何第三方代码。
- 以下项目仅用于**生成测试期望值**，其代码不进入本库：
  - `libsndfile`（经 `soundfile`）—— WAV 解码参照
  - `scipy` / `numpy` —— 重采样、FFT、窗函数、DCT 参照
  - `librosa` —— mel / log-mel / MFCC 参照
  - `pyloudnorm` —— ITU-R BS.1770-4 响度参照
  - `ffmpeg` —— 生成 WAV fixture
- 运行期唯一依赖：`moonbit-community/miniio`（WASIp1 I/O，MIT/Apache），且只被 `cmd/*` 技能使用。
- 标准依据：RIFF/WAVE（Microsoft/IBM）、ITU-R BS.1770-4 / EBU R128、RBJ Audio EQ Cookbook、
  Slaney mel 标度（librosa 默认约定）。

## 六、已知边界与未完成

**边界**（写进 README，不是藏着）：
- 只支持 WAV（RIFF），不做容器解封装
- 有调性的噪声（音乐、鸣笛）会被判成语音——谱特征靠"是否像噪声"否决，有调性的声音天然不像噪声
- 响度报告给的是样本峰值，不是真峰值（dBTP 需过采样）
- 重采样会保留 RIFF 保留块，其中含字节偏移的块偏移已失效

**未完成**（明确列出，不含糊）：
- 裸 PCM I/O、分块流式处理（大于内存的音频）、FLAC/OGG 解码
- 真峰值（dBTP）测量
- 音频数组视图原语（交错↔平面、分帧迭代器）

## 七、如果重来一次

1. **先建基准，再写实现**。VAD 的调参前期绕了远路，根因是没先做"特征分辨力诊断"——
   后来补上那一张诊断表（语音帧平坦度 0.19~0.28、白噪声 0.54~0.56）之后，阈值该定在哪一眼就清楚了。
2. **性质测试优先于示例测试**。完全重构、门控不变量、电平翻倍 = +6.02 LU 这类性质，
   覆盖的输入空间比任何手写用例都大。
3. **约定级的东西先去查参照实现**，别自己定。窗的对称性、mel 归一化、dB 的截断范围——
   每一条自己定都会让结果对不上生态，而且本地测试全绿也发现不了。
